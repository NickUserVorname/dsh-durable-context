    ```
    planner не задаёт уменьшенный budget без явной причины пользователя

    ```

    ```

4. **Compaction partial-commit robustness.**  
    При старом `missing 2302` surface replacement упал, но checkpoint уже стал:

    prune_safe_through_seq = 2319
    ```

    ```
    state/audit commit → PASS
    surface replace    → FAIL
    ```
    
    Лучше либо сделать атомарно, либо явно сделать retry-safe two-phase commit.
    
5. Ранее найденный **live-verifier false negative** тоже надо включить в пакет: verifier искал `state_checkpoint is OPTIONAL` не в том JS-файле.

### И что это говорит про архитектуру

Это скорее **PASS fail-closed дизайна**, но плохой out-of-box UX/template default: задача требует deterministic qualification, а новый проект приходит с пустым `TOOLCHAIN.json`.

Для прода я бы не убирал этот gate. Я бы исправил onboarding:

- либо `/task` при `qualification.mode=REQUIRED` заранее проверяет TOOLCHAIN и предупреждает **до `/work`**;
- либо planner умеет предложить verified task-specific commands;

Сейчас нам это не мешает выпуску: задаём два реальных теста, `/review`, `/accept` — и на этом qualification заканчиваем.

```
TEST_ANALYST (нейронка)
    ↓

    ↓

`sha256` в schema при этом **optional**.

То есть stochastic model фактически может заблокировать validation, просто вернув stale/неверный SHA. Это плохая граница доверия.

### Правильный фикс

**SHA должен принадлежать host'у, а не модели.**

Модель говорит только:

```
{
  "type": "artifact",
  "path": "...deterministic-tests.json"
}
```

А host:

1. проверяет, что artifact существует и внутри разрешённого evidence-root;
2. **сам считает текущий SHA256**;
3. записывает его в evidence ref;
4. потом валидирует/persist'ит уже sealed ref.

Так мы не ослабляем integrity — наоборот, убираем модель из криптографической trust boundary.
